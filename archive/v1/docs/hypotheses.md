# 가설 → 검증 기록

이 프로젝트의 주요 판단(라이프사이클 임계값, 세그먼트 분류 기준, 모델
feature 채택 여부 등)은 대부분 "이럴 것이다"라는 가설을 먼저 세우고,
실제 데이터로 검증한 뒤에 확정됐다. 이 문서는 `docs/methodology.md`(결정의
최종 근거와 결과)와 별개로 **가설 자체와 검증 과정**을 한곳에 모아두면
"왜 이렇게 설계했는가"뿐 아니라 "무엇을 먼저 의심하고 어떻게 틀렸는지
확인했는가"까지 추적할 수 있다.

형식: **가설 → 검증 방법 → 결과 → 반영 여부**. 가설이 틀린 것으로
확인된 경우, 처음 판단과 그걸 뒤집은 근거를 함께 남긴다.

---

## 1. 방문 10회 기준이 전환율 "변곡점"이다

- **가설**: `구매_직전_탐색형` 세그먼트가 쓰는 "방문 10회 이상" 기준이,
  전환율이 실제로 뚜렷하게 높아지는 지점(변곡점)일 것이다 — 애초에 이
  값을 "탐색_고객 방문횟수 분포의 p90"이라는 통계적 근거로만 정했기
  때문에, 이게 우연히 의미 있는 지점과도 일치하는지 확인이 필요했다.
- **검증 방법**: `visit_only`(검색 없이 방문만 한) 고객을 방문 횟수
  1\~9회는 1회 단위로, 그 이상은 10\~14/15\~19/20\~29/30\~49/50\~99/100+
  구간으로 나눠 구간별 실제 구매 전환율을 계산.
- **결과**: 9회(3.324%) → 10회(3.928%) 증가폭(+0.604%p)이 8→9회
  (+0.743%p), 10→11회(+0.546%p)와 비슷한 수준 — **10회를 경계로 갑자기
  꺾이는 지점이 없다.** 1회(0.049%)부터 100회+(29.981%)까지 매끄럽게
  연속 증가하는 곡선일 뿐, "변곡점"이라 부를 근거가 없었다.
- **반영 여부**: **가설 기각, 그러나 기준값은 유지.** "변곡점"이라는
  설명은 틀렸다고 인정하고 `mart_customer_segment.sql` 주석을 정정했다.
  다만 기준값(10회) 자체는 "상위 10% cut + 과접촉 방지"라는 별개의
  실무적 근거가 여전히 유효해 그대로 뒀다 — 근거가 틀렸다고 결론까지
  자동으로 틀린 건 아니라는 걸 확인한 사례.

## 2. 검색 1회 이상이면 고관여(구매 임박) 신호다

- **가설**: 탐색_고객 중 검색을 한 번이라도 한 사람은 고관여로 볼 수
  있다 — "탐색_고객의 90%가 검색을 전혀 안 해서 검색 존재 자체가
  이례적 신호"라는 추론에서 출발.
- **검증 방법**: 검색은 했지만 방문은 전혀 없는 고객(search_only)과,
  검색 후 방문까지 이어간 고객(search_first)의 실제 구매 전환율을
  분리해서 비교.
- **결과**: search_only 전환율 **7.75%** vs search_first 전환율
  **44.02%** — 거의 6배 차이. "검색 1회 이상"이라는 단일 조건이
  전혀 다른 두 행동 패턴을 하나로 묶고 있었다.
- **반영 여부**: **가설 기각, 조건 교체.** `mart_customer_segment.sql`의
  `구매_직전_탐색형` 분류 조건을 "검색 ≥1회"에서 "search_first(검색이
  방문보다 먼저)"로 교체(2026-08-07). 증분 집단 전환율이 5.80%→28.30%로
  개선.
- **시행착오 후속편**: 이 교체를 `mart_customer_segment.sql`에만
  적용하고 `mart_purchase_propensity.sql`(Model B 모집단 정의)은 그대로
  둔 채 넘어갔다가, 이후 감사 과정에서 "같은 판단을 두 곳에 독립적으로
  구현해서 한쪽만 갱신됐다"는 걸 뒤늦게 발견(2026-08-08). 모집단을
  21,119,640행으로 재정의하고 Model B를 재학습 — AUC는 미세하게
  하락(0.867→0.865)했지만, 모집단 정의 자체를 실제 의도("활동 고객")에
  맞게 정정하는 게 목적이었으므로 트레이드오프로 수용.

## 3. 장바구니 제거는 하나의 균일한 행동이다

- **가설**: 장바구니에 담았다가 뺀 고객은 "이탈"이라는 단일한 의미를
  가질 것이다 — 원래 `장바구니_이탈형` 세그먼트가 제거 시점 구분 없이
  하나로 묶여 있었다.
- **검증 방법**: add→remove 간격을 로그스케일 히스토그램으로 시각화.
- **결과**: 뚜렷한 이봉(bimodal) 분포 확인 — 짧은 쪽 봉우리(수 분)와
  긴 쪽 봉우리(수일\~수주) 사이 계곡이 약 4.3\~7.2시간 구간에 있었다.
  단일 행동이 아니라 최소 두 가지 서로 다른 패턴이 섞여 있었다.
- **반영 여부**: **가설 기각, 하위분류 도입.** 계곡의 중간값인 6시간을
  기준으로 `cart_removal_subtype`(fast_removal/slow_removal) 컬럼을
  `int_customer_cart_behavior.sql`에 추가(2026-08-08). fast_removal은
  관여도 중간(방문 54.35회)에 16분 만에 제거, slow_removal은 관여도
  최고(방문 96.52회)에 18.4일을 고민하다 제거 — 관여도와 제거 속도가
  반비례가 아니라 오히려 slow_removal 쪽이 더 적극적으로 탐색했다는
  점도 예상 밖이었다.

## 4. (3의 후속) "제거 이벤트가 없는" 고객도 이탈로 봐도 된다

- **가설**: `cart_removal_subtype` 도입 당시, remove 이벤트가 전혀 없는
  고객(`no_removal_recorded`)은 "아직 관측 기간이 부족해서 못 지운
  것"(우측 검열)이거나 "로깅이 빠진 것"일 수 있다고 의심했다 — 이
  집단이 세그먼트의 79.38%(1,406,964명)로 압도적 다수였기 때문에,
  원인을 확정하지 않고는 `장바구니_이탈형`이라는 이름을 계속 써도
  되는지 판단할 수 없었다.
- **검증 방법**: (a) remove 이벤트가 아예 없는지 vs add와 매칭만 안
  됐는지 구분, (b) 마지막 add부터 관측 종료일까지 남은 시간 분포 확인
  (시간 부족 가설 검증), (c) 담은 상품 개수 분포 확인.
- **결과**: 96.53%는 remove 이벤트 자체가 없음(매칭 실패가 아님) —
  로깅 문제 아님. 마지막 add 이후 관측 종료까지 남은 시간 **중앙값
  76일**, 87.9%가 종료 14일보다 여유 있음 — **시간 부족(우측 검열)도
  아님.** 76.1%는 상품 1개만 담고 다시 건드리지 않음 — "담아두고
  방치"에 정확히 부합.
- **반영 여부**: **가설(로깅/검열 문제) 기각, 세그먼트 자체를 분리.**
  "이탈"(능동적 거부, remove 있음)과 "보류"(미결정, remove 없음)는
  CRM 대응이 근본적으로 달라야 한다고 판단해, 참고용 컬럼 추가에서
  한 단계 더 나아가 세그먼트 자체를 `장바구니_이탈형`(20.62%)과
  `장바구니_보류형`(79.38%, 신설)으로 분리했다(8→9개 세그먼트,
  2026-08-08). 처음엔 "컬럼만 추가하면 충분하다"고 판단했다가, 다수가
  압도적으로 크고 CRM 목적 자체가 달라야 한다는 걸 재확인하고 판단을
  뒤집은 사례.

## 5. category 컬럼은 상품 간 실제 유사성을 반영한다

- **가설**: `product_properties.category`(익명 정수 ID)가 상품명 기준
  유사성과 대체로 일치할 것이다 — 두 카테고리에 속한 상품은 실제로도
  비슷한 상품일 것이라는 암묵적 전제.
- **검증 방법**: 상품명 임베딩을 MiniBatchKMeans로 클러스터링(k=50,
  Kneedle 엘보우로 결정)한 뒤, 기존 category 라벨과 일치도를 NMI/ARI로
  계산.
- **결과**: NMI **0.1258**, ARI **0.0137** — 둘 다 0(무관)에 가깝다.
  category가 같다는 사실이 "상품명 기준으로도 유사하다"를 거의
  보장하지 못했다.
- **반영 여부**: **가설 기각.** category를 "느슨한 운영 분류"로만
  취급하기로 하고, `docs/limitations.md`에 caveat을 기록. 이 전제 위에
  있는 두 산출물(`avg_category_repurchase_rate` feature, 세그먼트의
  "카테고리 기반" 추천 액션 문구)에 명시적으로 링크해뒀다 — feature나
  문구 자체를 없애지는 않았지만, 해석 시 주의가 필요하다는 걸 문서화.

## 6. 카테고리별 재구매율은 표본 부족으로 계산할 수 없다

- **가설**: Phase 3 퍼널 분석 작성 당시, "구매 고객당 평균 카테고리 수가
  1.70개로 다양성이 크지 않아 카테고리별로 쪼개면 표본이 너무 작아질
  것"이라고 판단해 계산을 시도하지 않고 "Phase 4에서 다룬다"고만 적어둠.
- **검증 방법**: (뒤늦게) 카테고리별 고객 수 분포를 실제로 확인하고,
  최소 표본 기준(카테고리당 100명)을 적용해 실제 재구매율을 계산.
- **결과**: 전체 6,337개 카테고리 중 다수(중앙값 35명)는 실제로 표본이
  작았다 — 이 부분은 원래 우려가 맞았다. 하지만 최소 표본 기준을
  적용해도 **2,074개 카테고리(32.7%)가 통과했고, 이들이 전체 구매의
  93.6%를 커버**했다. 그 안에서 카테고리 간 재구매율 차이는 결코
  작지 않았다 — 카테고리 1096(28.59%), 2964(20.79%)는 전체 평균(7.18%)
  대비 3\~4배 높았고, 이항분포 근사 z-검정에서도 z=95.9, 55.5로 우연이
  아니었다.
- **반영 여부**: **가설 절반만 기각.** "표본이 부족한 카테고리가 많다"는
  맞았지만, "그래서 계산 불가능하다"는 틀렸다 — 정확히는 "최소 표본
  필터링 없이 시도조차 하지 않았던 것"이었다. Phase 3 리포트를 정정하고,
  `avg_category_repurchase_rate`를 새 intermediate 테이블 체인
  (`int_customer_category_repurchase_by_snapshot` →
  `..._avg_by_snapshot`)으로 구축해 Model A/B feature로 추가했다.
  Feature importance는 Model A에서 13개 중 9위(중간 기여), Model B에서
  8개 중 8위(꼴찌) — 같은 feature가 모집단 구성에 따라 얼마나 다르게
  기여하는지도 함께 확인됨(Model B는 구매 이력 없는 고객이 다수라
  이 feature가 NULL인 비중이 높음).

## 7. price_bucket과 전환율은 대체로 선형 관계다(가격이 낮을수록/높을수록 전환율이 다를 것)

- **가설**: 별도로 세운 적은 없지만, price_bucket별 전환율을 처음
  볼 때 "가격이 낮을수록 전환이 쉽거나, 비쌀수록 전환이 어려울 것"이라는
  단조적 관계를 기본적으로 예상했다.
- **검증 방법**: price_bucket 0\~99 전 구간의 장바구니 추가→구매 전환율,
  제거율을 전수 계산.
- **결과**: 굴곡형(hump-shaped) 패턴 — bucket 0(20.47%)에서 시작해
  **bucket 59 부근에서 24.08%로 최고점**을 찍은 뒤 bucket 99(11.65%)로
  하락. 양 극단보다 중간\~중상위 구간의 전환율이 더 높았다. 단순 선형
  상관계수만 봤다면 "가격이 낮을수록/높을수록 전환율이 높다"는 잘못된
  단조적 결론으로 오도됐을 상황.
- **반영 여부**: **암묵적 가설 기각.** price_bucket이 실제 금액이 아니라
  순위형 구간값이라 원인(중간 가격대 상품 구성 차이 등)을 확정할 근거
  컬럼이 없었다. 원인 불확정 상태에서 모델 feature나 세그먼트 기준으로
  쓰는 건 근거가 약하다고 판단해, `docs/limitations.md`에 "참고용 관찰,
  원인 미확정"으로만 기록하고 파이프라인에는 반영하지 않았다.

## 8. 라벨을 희소하게(60일) 만들면 Model A의 Lift가 개선된다

- **가설**: `reports/phase6_modeling_results.md`에 이미 "라벨 양성률이
  90%대로 이미 다수 클래스라 Lift가 1.04\~1.10 근처에서 상한을 찍는다,
  Lift는 base rate에 종속된다"는 서술이 있었다 — 그렇다면 라벨을 더
  희소하게(양성 비율을 다수 클래스에서 더 멀어지게) 만들면 Lift가 실제로
  올라갈 것이라는 가설을 직접 라벨을 바꿔서 재현·검증하고 싶었다. Model
  A의 churn 라벨을 기존 14일/28일 대신 60일(생애주기 비활성 임계값,
  구매간격 p90=68.05일 근거, PROJECT_GUIDELINES.md 17번 관련 임계값 확정 항목)로
  늘려서 확인.
- **검증 방법**: 60일 라벨은 우측 검열 제약상(라벨 윈도우가 관측 종료를
  넘으면 안 됨) 기존 9개 snapshot 중 6개(가장 이른 시기, 07-21\~09-29)만
  안전하게 쓸 수 있어, 처음엔 이 6개로 churn_60d를 계산해 LightGBM을
  학습했다. 하지만 이러면 원래 churn_14d/28d 결과(9개 snapshot, 더 늦은
  시기 test)와 시기가 달라 직접 비교가 안 된다는 걸 깨닫고, 통제 실험을
  다시 설계했다 — 동일한 4개 train/1개 val/1개 test snapshot(전부
  07-21\~09-29 구간 내)으로 churn_14d/28d/60d를 전부 재계산·재학습해
  라벨 윈도우 길이만 유일한 변수로 남겼다. 프로덕션 마트/학습 스크립트
  (`sql/marts/mart_customer_snapshot.sql`, `mart_churn_target.sql`,
  `scripts/train_model_a.py`)는 건드리지 않고 별도 스크립트로만 수행.
- **결과**: 통제 실험에서 양성률·AUC·Lift@10%가 전부 단조적으로
  움직였다 — churn_14d(양성률 94.65%, AUC 0.7433, Lift@10% 1.038) →
  churn_28d(90.77%, 0.7312, 1.063) → churn_60d(83.95%, 0.7109, 1.105).
  **라벨이 희소해질수록(양성률이 다수 클래스에서 멀어질수록) Lift는
  정확히 예측대로 올라갔다.** 하지만 동시에 AUC는 오히려 떨어졌다 —
  모델의 실제 랭킹 능력은 60일 예측에서 더 나빠졌는데(예측 시계가
  길수록 신호 대비 잡음이 커지는 건 잘 알려진 현상), Lift 숫자만 보면
  정반대로 "더 좋아진 모델"처럼 보인다.
- **반영 여부**: **가설 부분 확인, 그러나 실무 결론은 반대 방향.**
  "라벨을 희소하게 만들면 Lift가 개선된다"는 문자 그대로는 맞았고,
  `phase6_modeling_results.md`의 "Lift는 base rate에 종속된다"는 서술이
  실제로 라벨을 바꾼 실험으로 실증됐다. 다만 이건 "60일 라벨이 더 나은
  타겟"이라는 뜻이 아니라 정확히 반대다 — **Lift 개선이 모델 품질
  개선을 의미하지 않는다는 함정을 재현한 것.** AUC(라벨 base rate에
  영향받지 않는 더 공정한 척도)로 보면 14일이 여전히 가장 예측하기
  쉬운(=신뢰할 수 있는) 타겟이라, Model A의 실제 라벨은 14일/28일
  그대로 유지했다 — 파이프라인 변경 없음. 결과는
  `reports/adhoc_churn_60d_hypothesis_test.csv`(60일 라벨 전체 결과),
  `reports/adhoc_churn_controlled_comparison.csv`(통제 비교)에 저장.
